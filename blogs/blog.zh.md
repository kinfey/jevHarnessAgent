# 一份汉堡套餐，带我重新理解 Agent：Jev、LLM 与 Model Router 的分工

> 当 AI 已经能写代码、查菜单、调用工具，我们还需要什么？这个项目给我的答案是：除了一个聪明的大脑，还需要一套清楚的工作分工。

晚上准备离开办公室，我对 AI 说：

“帮我看看附近麦当劳的一份板烧鸡腿堡套餐，中杯可乐，到店取餐。先算价格，不要下单。”

对人来说，这是一句很普通的话。但对软件来说，它至少包含六个判断：吃什么、几份、什么规格、喝什么、如何取餐，以及允许执行到哪一步。

随后还有一串真实世界的问题：哪家店有货？套餐包含什么？优惠券适不适用？最后需要多少钱？

我们围绕这份套餐搭了一个小实验：同一个页面，左边运行 Jev Harness，右边运行传统 GitHub Copilot Agent。两边都通过 GitHub Copilot Python SDK 使用 `gpt-6-astra`，访问同一个麦当劳中国 MCP 服务。

这里的重点不是“哪一个 AI 更会点餐”，而是：**哪些事情值得交给大模型思考，哪些事情应该由程序明确安排？**

## 一、传统 Agent 和 LLM 的关系：主厨不等于整间餐厅

如果把 AI 系统比作一家餐厅，LLM 就像一位经验丰富的主厨。

你说“我想吃清淡一点”，主厨能理解；你临时改主意，他也能重新安排。他擅长处理开放式问题，而不是只能沿着固定按钮前进。

但只有主厨，餐厅并不能营业。还需要接单、库存、收银、权限和工作流程。

这就是 Agent 与 LLM 的区别。**LLM 提供理解、推理与生成能力；Agent 是围绕模型构建、能使用工具并推进任务的系统。** Harness 则是承载它的运行框架：把什么上下文交给模型、允许调用哪些工具、如何接回结果、什么时候停止。

在典型的工具调用循环中，流程大致如下：

```text
用户提出需求
    → LLM 判断下一步
    → Harness 执行工具
    → 工具结果加入上下文
    → LLM 再判断下一步
    → 完成或继续
```

它非常灵活。Coding agent 遇到测试失败，可以读日志、找代码、修改实现，再运行测试。麦当劳点餐助手也可以先查门店，再看菜单，最后试算。

代价是，主厨可能连“这是外送还是自取”“接下来应该打开哪个菜单”都要亲自处理。每轮都涉及模型请求、上下文处理和工具等待。随着工具结果不断加入，账本也越来越厚。

当然，传统 Agent 不是必然低效。它同样可以使用结构化输出、工具白名单、并行调用和确定性工作流。问题不是“LLM 不行”，而是**我们是否把所有工作都默认交给了同一种执行方式**。

## 二、什么是 Jev：不写作文，而是填写软件可以使用的订单

TypeSafe 在 [Introducing System One Models & Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev) 中介绍了 Jev：它是该公司首个公开的 System One 模型，发布时处于早期访问阶段。

名称借用了“快思考、慢思考”的比喻，但不需要把它理解成人类大脑的精确复制。

更实用的理解是：**Jev 接收状态与预先定义的问题，返回带概率信息的类型化判断，而不是自由生成一段文字。**

回到餐厅。传统 LLM 可以解释“为什么这份套餐适合你”；Jev 更像负责理解顾客表达、在订单选项上打勾的接单员。

TypeSafe 提供三种基本问题：

| 类型 | 通俗理解 | 例子 |
|---|---|---|
| `Choice` | 从已定义的选项中选择 | 自取、外送、堂食，还是未说明？ |
| `Noul` | 判断一个命题为真的概率 | 用户是否明确要求只试算？ |
| `Score` | 根据有序标准评价 | 这次操作的影响程度属于哪一档？ |

本项目只使用 `Choice`：把六个判断放进一次 `system_one` 请求，而不是先问餐点、再问饮料、再问取餐方式。按 TypeSafe 的设计，这些问题可以在同一请求中并行评估。

`Choice` 的返回不仅包含选项，还包含概率分布和 `confidence`。两者不要混为一谈：选项概率描述各候选答案的分布，confidence 是另外一个用于表达确定程度的指标；更不能把一次 confidence 为 0.99 理解成“这张订单有经过证明的 99% 正确率”。

TypeSafe 将其训练方法称为 **RLCD，Reinforcement Learning for Calibrated Decisions**，目标是让概率与实际表现更匹配。这是值得关注的方向，但阈值仍需要在自己的任务数据上校准。

还有一个重要边界：发布文章强调类型安全，并使用了“不会幻觉”的表达。工程上应当把这与“永远判断正确”区分开。

**只能从菜单中选，不代表一定选中了顾客想吃的菜。**

Jev 仍可能误解需求。它不负责生成代码、不适合承担精确算术，也不能仅凭一个判断就授权付款或部署。符合 schema、语义正确和获得执行权限，是三件不同的事。

## 三、和 Model Router 的区别：选哪位主厨，还是决定订单怎么流转？

这时很容易产生一个疑问：“这不就是 Model Router 吗？”

可以先想象餐厅经理面对两个问题：

“这桌菜交给哪位主厨？”  
“这张单是自取还是外送？信息是否完整？能不能交给收银台？”

前一个更像 Model Router，后一个更接近我们使用 Jev 的方式。

| 维度 | Model Router | 本项目中的 Jev |
|---|---|---|
| 主要问题 | 哪个模型或端点适合处理这次请求？ | 当前请求属于什么状态，应该走哪个业务分支？ |
| 常见依据 | 难度、成本、延迟、模型能力、可用性 | 用户表达、候选选项、概率和信心门槛 |
| 常见结果 | 选择模型 A、B，或备用端点 | 自取、标准套餐、只试算、需要人工确认 |
| 本项目是否切换生成模型 | 没有实现此类路由 | 两条路径都使用 `gpt-6-astra` |

Router 是一种架构组件，Jev 是一种模型，二者并不是同一层级的替代品。

它们也完全可以配合：让 Jev 判断任务类别或复杂度，再由路由策略选择一个模型。但模型选择、预算和故障转移仍然需要程序实现，Jev 不会自动提供一整套 Model Router。

因此，本项目不是“Jev 把 GPT 换成了另一个更快的模型”。**GPT-6-astra 没有被替换，被调整的是它前面的任务分解，以及它运行时携带的上下文和工具。**

## 四、Jev 带来的改变：让主厨少管杂事，让规则回到程序

最值得讨论的变化，不是 JSON 长什么样，而是责任如何分配。

原来的路径，把自然语言需求直接交给 Agent，让它一边理解、一边执行。新的路径先形成有限、可检查的决策，再让本地程序决定是否继续，以及暴露哪些工具。

```text
自然语言需求
    → Jev API：理解为有限选项与概率
    → 本地 Python gate：检查门槛、字段与权限
    → Copilot SDK / Runtime：执行工具调用循环
    → GPT-6-astra + MCP：查询、组合结果、生成回答
```

这里的 **Python gate 既不是另一个 AI API，也不是 CLI**。它就是本地 Python 逻辑：检查最低 confidence 是否达到默认的 `0.75`，检查取餐方式、主餐、饮料是否缺失，并依据计划缩小工具集合。`0.75` 是演示配置，不是通用的安全标准。

Jev 通过 TypeSafe Python SDK 调用远程 API；Copilot Python SDK 则控制底层 runtime。不要因为都写在 Python 里，就把这些边界混在一起。

从 coding agent 的角度看，这种分工很有启发：

“帮我修复这个测试”仍然需要强大的生成式模型理解代码、提出补丁。但任务是否只是查询、是否涉及数据库迁移、需要哪组工具，可以先做范围有限的判断。然后由程序决定允许读哪些路径、能否写入、必须运行哪些检查。

这只是从点餐项目延伸出的架构方向，当前代码并没有实现完整的代码修改工作流。并且，“模型认为风险低”不能替代沙箱、权限检查和测试。

同样需要坦诚的是：**当前 Jev Harness 也没有彻底移除 Agent loop。** Python 确定性地执行前置门槛和工具过滤；后续五工具流程主要写在提示中，具体调用和参数仍由 GPT-6-astra 选择。它是一个混合原型，不是已经由程序强制所有状态迁移的工作流引擎。

## 五、结合项目：一份板烧鸡腿堡套餐，经历了什么？

### 接单：先让机器看懂订单

实验需求是：一份板烧鸡腿堡套餐，中杯可乐，在广州附近门店自取，只做价格试算。

传统路径接收原始请求。Jev 路径则先在 `src/harness_agent/jev.py` 中完成六个 `Choice`。程序把答案整理成如下订单计划；这是计划形状的示例，不是完整 API 原始响应：

```json
{
  "fulfillment": "pickup",
  "meal": "grilled_chicken_combo",
  "size": "regular",
  "drink": "coke",
  "quantity": 1,
  "action": "quote_only"
}
```

套餐名称可以落在预定义选项里，但门店位置是开放文本。开发时我们就踩过这个坑：只传六个字段，执行器不知道去哪里找店。

解决方式不是让 Jev 编造地址，而是把原始请求作为位置上下文一并交给执行器。类型化决策很有用，却不意味着可以丢掉所有未结构化信息。

### 执行：让每个组件只做自己的事

通过 Python gate 后，自取路径只开放五个 MCP 工具：

```text
query-nearby-stores
    → query-meals
    → query-meal-detail
    → query-store-coupons
    → calculate-price
```

这是一张依赖关系的简化示意，而不是要求所有操作都串行。取得门店后，某些菜单和优惠查询可以独立进行；但价格试算必须等商品及搭配明确之后。

商品编号、套餐组成和价格来自实际 MCP 返回，不由 Jev 凭空生成。一次成功执行匹配了板烧鸡腿堡、中薯条和中杯可乐，试算总额为 **人民币 34.50 元**。查到的两张券不适用，没有为了凑优惠擅自加购。

这是当时门店的报价，不是长期有效的全国统一价格。

页面路径不开放 `create-order`，目标是“真实查询，模拟下单决策”，并不真的买下一份套餐。CLI 的显式提交模式是另一个能力；这个故事只讨论报价演示。

### 调优：最快的一次，曾经没有完成任务

最初，我们只是把 Jev 加在原有 Copilot Harness 前面，结果没有出现想象中的巨大飞跃。

这很正常。接单员虽然填好了单，主厨还是带着整本员工手册、大量无关工具和完整运行环境进入厨房。多一个分类请求，并不会自动消除后续的成本。

于是，Jev 路径改用 Copilot SDK 的 `empty` mode，显式指定工具，关闭不必要的 skills、session store 和配置发现，并让 runtime 启动与 Jev 分类重叠。回答也收敛为简短报价表。

但第一次精简后的执行有个危险的“好成绩”：大约 28.8 秒就结束了，却因为菜单输出被截断、又没有读取完整输出的工具，**根本没有完成计价**。

如果只看秒表，它赢了；如果看用户任务，它失败了。

随后我们让大菜单结果保持 inline，恢复了完整试算。这是一种取舍：减少取文件的回合，但也把更多菜单内容放回模型上下文。它适合本次演示，未必适合无限增长的菜单。

以下是开发期间控制台记录的几次单次观察，**不是同一版本、随机化顺序、多轮统计的正式 benchmark**：

| 指标 | 传统 Harness 历史运行 | 初版 Jev Harness | 调优后 Jev Harness |
|---|---:|---:|---:|
| 全链路耗时 | 113.28 秒 | 92.68 秒 | 35.41 秒 |
| Copilot usage 事件数 | 10 | 7 | 5 |
| 工具执行开始事件数 | 10 | 7 | 5 |
| 累计 input tokens | 251,438 | 177,421 | 125,924 |
| 累计 output tokens | 2,435 | 1,898 | 836 |
| 完成价格试算 | 是 | 是 | 是 |

Jev 两列的 token 合计包含 Jev API 与 Copilot 各轮用量。累计 input 会重复计算各轮传入的历史上下文，并包含缓存相关用量，不能直接当作唯一文本长度或全部未缓存的计费输入。工具事件数也不应在缺少逐工具核对时直接标成“纯 MCP 请求数”。

调优后这个样本相对传统历史样本的耗时低约 68.7%，但**不能把这个百分比全部归功于 Jev**。Runtime、上下文、工具配置、回答长度和执行时的服务状态都不同。传统路径也能采用其中许多优化。要分离 Jev 本身的收益，应增加一个同样精简、同样输出要求但不使用 Jev 的对照组，再比较多轮成功率、p50/p95 与实际账单。

TypeSafe 发布文章中的“193.6 倍更快、444.6 倍更便宜”来自其特定 System One 工作流评测，既不是这个项目的数据，也不是整个点餐流程的承诺。SDK 返回 `output_tokens` 也不代表该字段一定按生成式模型相同方式收费；用量和价格需要分别解释。

### 看见过程：让演示从秒表变成实验台

为了把这些差别看清楚，我们做了一个 light-only 的双栏 Dashboard，支持简体中文、繁体中文和英文。

点一次按钮，两条路径同时运行。后端用 chunked NDJSON 推送事件，左右控制台实时显示决策阶段、模型回合、工具开始与完成，以及 usage。结果区再展示 Jev 的结构化 JSON、应用发送的 Agent 上下文和 token 明细。

这里展示的是可观测执行事件与应用上下文，不是模型隐藏的思考过程，也不等于 SDK 最终拼装的全部内部提示。

安装项目并配置凭证后，可以这样启动：

```bash
harness-dashboard
```

在浏览器打开 `http://127.0.0.1:8765`。`YOUR_MCP_TOKEN` 与 `TYPESAFE_API_KEY` 放在本地 `.env`，不要放进网页或文章。

同时竞跑适合演示，但会受到网络、服务限流和缓存状态影响。真正要做严谨评测，还是要固定版本与成功标准，多次运行，并检查每次是否真的拿到了正确报价。

回到那份汉堡。我最想分享的，并不是“又出现了一个更快的模型”，而是一个更朴素的工程观念：

**让 LLM 处理开放问题，让 Jev 处理有限判断，让程序握住权限与流程。**

好的 Agent，不一定是拥有更多自主权的 Agent，也可能是终于学会合理分工的系统。
